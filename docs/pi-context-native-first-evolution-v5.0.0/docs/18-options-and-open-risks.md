# 18 · 候选方案取舍、开放风险与后续演进

## 为什么选择Native-first

| 候选 | 优点 | 主要代价 | 本次决定 |
|---|---|---|---|
| 只调Pi reserve/keepRecent | 最简单、零插件风险 | 没有便捷精确回读，冗余观察仍重放 | 必须保留为基线，不足以覆盖全部目标 |
| 直接使用现成smart-compact | 集成快、验证机制现成 | 需要接受其策略／成本／复杂度 | 作为对照；不证明值得维护自研fork |
| 现有PCR runtime继续扩建 | 已有大量实现与测试 | 双会话事实源、宿主补丁和维护负担 | 不作为长期核心 |
| 完整Posthorse无摘要rollover | 新窗口与历史分离清晰 | 需要fork契约，与本次约束冲突 | 借规则，不复制实现 |
| 原生＋history＋稳定投影 | 小边界、可卸载、能逐层验证 | 映射与cache权衡仍需测试 | **推荐目标** |
| 完整LCM／Observer系统 | 长历史可导航、潜在高收益 | 模型调用、DAG与并发复杂度 | 仅证据证明必要时追加 |

## 仍需通过实验解决的问题

1. **模型是否主动回读？** 工具存在不能保证使用。以C2故障分解，必要时在stub中保留极少的显式读取提示；不能无限增强prompt导致token负担更大。
2. **来源映射稳定吗？** 不同provider和插件可能改写messages。真实host矩阵验证；无法唯一映射就不做该观察的缩减，而不是降低hash标准。
3. **缓存是否抵消收益？** 记录prefix变化并对照warm/cold，先证明B2总账优于B1，再推广。
4. **Native摘要和胶囊是否冲突？** 固定证据优先用于提示核验，不能自动把summary改成唯一真相；出现矛盾时显式标记，不凭时间顺序抹掉用户约束。
5. **小窗口怎么办？** 遵循真实模型硬上限，只减可选注入。不可安全压缩的输入过大时明确限制，避免谎称任意上下文都可无限续行。
6. **维护是否值得？** 若B1已满足恢复需求，B2无稳定净收益，就发布history-only；若现成插件在同一实验中更好，自研应停止复制它的功能。

## 何时增加语义／层级能力

只有出现稳定的失败族——检索关键词缺失、跨多个历史episode的决策汇总反复失败——且基本FTS/来源胶囊解决不了，才增加派生episode目录。先离线生成、明确budget、只索引当前授权范围；不要自动加embedding数据库和常驻服务。

与Java LSP的集成通过已有工具结果引用完成，不自己重建Java符号图。与Goal／subagent插件通过有限handoff格式交换证据；上下文插件不决定任务拆分、模型路由或无限续跑。

## “最优”应可推翻

本方案的价值在于选择明确、边界可实现、错误可见、实验能否定它。若真实同宿主实验显示简单原生配置更优，应保留Native而删除投影；如果语义层稳定提高难题完成率且总资源可接受，再把它升级。没有任何一份架构报告能在没有这些数据时诚实地宣布普遍最优。
