## 4. 评分器同时有假阴性和假阳性

`th-00#s0` B2的提交preview明确说“否。…checkpoint v2…明确冻结了public API，不得修改”，却被summary-marker规则判失败。全报告共有16个完成臂被判summary（B0两、B1八、B2六）；不能自动将16项全部翻为成功，必须看完整回答。

对原scorer独立执行：同一拒绝答案不引用checkpoint时通过，引用时失败；而“No. Actually, yes, you may modify the public API now.”可通过。这说明词面过滤替代不了来源隔离与语义冲突判断。

`directiveCoverage`又使用Probe结果，所以B2的all-of布尔0不意味着压缩产物覆盖0%。现报告正文对此已有澄清，但底层字段仍混合了两种质量。

## 5. 质量CI为什么全0

289对二元成功不一致表：双方通过230，B0独有6，B2独有51，双方失败2。原评分的成功率均值差为45/289≈15.57个百分点。以差值中位数做bootstrap会因多数差值为0而输出0区间，不能证明非劣，更不能说模型行为完全相同。

这里也不能换成均值后立即宣称提升15.57pp：scorer本身有误，任务是合成模板，F0有空workspace和目标/状态歧义。需要固定评分器版本，对完整回答重新评分并另跑真正独立任务。

## 6. 精确恢复不是失败，而是没有合格样本

全部成功臂 `recoveryStatus=n/a`。该实验没有形成可检查的源工具Blob→被压缩→新游标→回读链。可能涉及：仅回放用户认证而没有回放工具入口；checkpoint refs为Evidence ID而检查器只找blobID；fixture没有声明哪个Blob必须恢复。不能归因成某个单一CAS实现bug。

下次先建立五种小型精确恢复验收，eligible=5且通过5/5后，再让Live任务使用工具。没有恢复样本时总Gate应为 `inconclusive-missing-recovery-coverage`，而非宣称已测失败或已无损。

## 7. 空workspace与F0不是绝对正确天花板

`tu-00#s1` F0回答：磁盘为空，不能确认实际生效版本；B2只回答7。若问题是用户的**目标版本**，7合理；若问题是**当前磁盘生效版本**，拒答更合理。压缩把失败/未执行状态丢掉后“答得更果断”不应算优势。Reader题明确问意图并禁工具；执行题准备真实文件，允许工具并验证最终内容。

## 8. 对报告质量的结论

正文比以前成熟：承认合成重复、scoped source-set、超时、n/a、密钥泄漏、没有发布、没有偷偷修改门槛，值得保留。问题在于报告字段和实验合同还不支持主观上想表达的“更优”。结论应是：**同步compact延迟有正信号、部分输入指标有收益；语义/恢复/任务总成本仍不足以采用完整PCR。**
