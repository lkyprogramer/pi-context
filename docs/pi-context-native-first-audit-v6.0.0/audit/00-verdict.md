# 结论：路线收敛正确，balanced 尚未被当前试验验证

## 1. 本轮真进步

本分支从PCR多包/宿主补丁退回到单一官方Pi扩展，src约2千行；默认observe，不拦截工具结果，不改用户输入，不自带第二事实源。原生日志、祖先关系与原生compact仍由Pi负责。真实打包安装和容器内编码环境的建设有价值，不能继续引用旧main的编译错误批评这份代码。[S01–S03]

**最重要的纠偏：实现评估基线是分支里的 `docs/pi-context-native-first-evolution-v5.0.0` 的26项任务。** 前轮S01–S10和旧PCR几十项任务仅作历史背景，不能强制搬回来。

## 2. 当前结论

- **默认observe**：不改变请求消息，原生压缩仍可使用。history有功能信号，但分页、字段引用与跨session索引问题必须先修；不建议现在在敏感多会话环境依赖它。
- **balanced**：当前配置未真正加载、暴露快照匹配不完整、冻结epoch未冻结、引用不可读、胶囊目标消息错误。暂停推荐。
- **experimental-semantic**：明确关闭是正确的产品边界，不是需要立刻补齐的缺陷。
- **报告的limited-trial**：最多支持“当前默认插件能加载、若干简单Java任务仍可完成、引导式历史工具曾完成恢复”。不支持“balanced压缩更优”。

## 3. 最主要的三个根因

第一，**端到端合同缺失**。`config.ts`、`ExposureLedger`、`HistoryIndex`、capsule函数分别存在，但入口没有使用真实配置、事件字段、字段级hash及完整snapshot。实际模块测试能复现，不是模型随机波动。

第二，**实验臂标签代替了机制证据**。G4称候选B2，但没有设置balanced；entry使用DEFAULT_CONFIG=observe。于是研究问题写的是“减少历史”，真正测的是“增加一个history工具”。

第三，**测试问题与记忆问题不一致**。J03/J04最后一条任务直接写出修法，J08在没有可压缩历史时调用compact并忽略失败；J05要求两边都调用只有插件一侧存在的工具。它们可作功能样例，但无法说明长程上下文质量。

## 4. 本轮不要做什么

不再换底层框架，不维护Pi fork；不因没有100×3拒绝个人试用；不因单元测试很多宣布正确；不因已成功回读一次就放宽所有来源权限；不为了通过质量门修改同版本测试题；不把零次发生的压缩算作压缩成功。

最优的实际路线是：**修正引用/权限/分页 → 真实宿主事件及暴露 → 可测的冻结投影 → 可选、极小的pin胶囊 → 同工具集的小型质量实验。** 

这是一项约束下的工程推荐，不是已经数学证明或通过跨模型实验的全局最优。若完整请求成本没有改善，停在原生压缩+安全history就是有效成果。
